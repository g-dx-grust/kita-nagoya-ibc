# Phase 0-3: 既存と新規の境界線確定

## 使用ツール

Claude Code

## 目的

0-1（DB ギャップ）・0-2（API/ロジックマッピング）・0-A（画面）の結果を踏まえ、Phase 1 以降の実装で **「既存テーブル拡張」と「新規テーブル分離」のどちらを取るか** をテーブル単位で決める。**この出力が Phase 1 の Codex プロンプトの入力になる**。

## 前提

- 0-1, 0-2, 0-A が完了して `docs/phase_0_outputs/` に出力されている前提（無ければ Stop して指摘）。
- 既存画面のデザインを崩さないため、**既存テーブルへの破壊的変更は最終手段**。
- 出力先：`docs/phase_0_outputs/0_3_boundary_decision.md`

- `docs/phase_0_outputs/0_2_api_logic_audit.md`

## やってほしいこと

1. 0-1 のギャップ表で「部分的にある」テーブル1つずつに、**判断**を付ける：
   - **A. 既存テーブルにカラム追加**（破壊しない範囲、NULL 許容 + デフォルト値で増設）
   - **B. 既存テーブル温存 + 新規テーブル追加**（拡張部分を別テーブルに切る）
   - **C. 既存テーブル置換**（マイグレーション計画を立てる）
   - 判断理由を1行で書く。
2. 「無い」テーブルは原則 **新規追加**。命名規則（snake_case、複数形）、`active`／`valid_from`／`valid_to` 命名の統一を宣言。
3. 既存 API のレスポンス互換性ルールを明文化：
   - 既存フィールドは削除しない
   - 既存フィールドの型は変えない
   - 追加フィールドは null 許容、デフォルト挙動が既存と同じ
4. **Phase 1 で着手する範囲**を確定（チケットレベル）：
   - 1-1〜1-7 のうち、既存があるもの／無いもの／拡張だけのもの
   - 各サブタスクの想定工数感（S/M/L）
5. **Phase 1 で触らない範囲**を明示（既存マスタの画面・既存 API のレスポンス・layout.tsx・globals.css・UI コンポーネント）。
6. デザイン保護ルールを箇条書きで宣言：触ってよい場所と触ってはいけない場所を `app/src/` のディレクトリ単位で列挙。
