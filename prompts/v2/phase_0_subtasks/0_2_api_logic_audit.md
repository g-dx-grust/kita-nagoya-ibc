# Phase 0-2: 既存API・既存ロジック調査

## 使用ツール

Claude Code

## 目的

既存の API ルート（`app/src/app/api/`）と計算ロジック（`app/src/lib/`）に何があり、docs/18 の Phase 1〜9 の機能とどう対応するかを表にする。**新規実装で重複を作らない／既存に乗せる**ための基礎資料。

## 前提

- 既存 API のレスポンス仕様は**現状の正**として読む（書き換えない）。
- 既存ロジックの責務境界を理解した上で、docs/18 のサービス層をどこに足すか **判断材料を集める**段階。
- 出力先：`docs/phase_0_outputs/0_2_api_logic_audit.md`

## 読むファイル

- `app/src/app/api/` 配下すべて（route.ts を中心に）
- `app/src/lib/` 配下の全 .ts（テストファイル含む。テスト名から責務を読み取る）
- `docs/11_api_contract.md`
- `docs/18_implementation_phase_plan.md` の実行時パイプライン（§13）と並列処理（§14）

## やってほしいこと

1. **既存 API エンドポイント一覧**を作る：HTTP メソッド、パス、入出力の概要、依存しているライブラリ／lib 関数。
2. **既存 lib モジュール一覧**を作る：ファイル名、エクスポート関数、責務、対応するテストファイルの有無。
3. **docs/18 の機能 ↔ 既存実装マッピング**を作る：
   - Phase 1（マスタ CRUD）
   - Phase 2（在庫推移計算）
   - Phase 3（生産予定登録、所要時間計算、BOM 展開）
   - Phase 4（原料使用予定、リードタイム逆算、発注候補）
   - Phase 5（日報、実績反映）
   - Phase 6（手間賃、原価、伝票出力）
   - Phase 7（CSV 取込）
   - Phase 8（需要予測、月間→日別割当、シナリオ）
   - Phase 9（異常検知、自動再計算）
4. **重複しそうな箇所**を別表で抽出（例：`monthly-production-forecast.ts` と Phase 8 の `monthly_production_plans` 計算が被るなど）。
5. **既存 API のレスポンス互換性に注意が必要なエンドポイント**を列挙（外部から叩かれている可能性、既存画面が依存している）。
6. `app/src/lib/audit.ts` の使われ方を確認し、Phase 4・5・6 で監査ログがどう載るかメモ。

## 完了条件

- ファイルが書き出されている。
- `app/src/app/api/` 配下の route.ts がすべて表に出ている。
- `app/src/lib/` の .ts（テスト除く）がすべて表に出ている。
- docs/18 の Phase 1〜9 すべてに「既存有/部分/無」の判定がある。

## 絶対にやらないこと

- `app/` 配下の編集。
- API を叩いて挙動確認（`curl` 等）。
- リファクタの実施。
- 「ここをこう書き換える」という具体的なコード提案（**マッピングと方針メモまで**）。
