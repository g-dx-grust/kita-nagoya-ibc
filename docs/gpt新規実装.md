# まず全体方針

## 既存システムへの追加方針

既存システムを壊さないために、基本方針は以下です。

1. **既存画面・既存テーブルを直接大改造しない**
2. まずは追加テーブル・追加サービスで拡張する
3. 自動計算結果は、いきなり本データに反映せず、まず「生成候補」として保存する
4. 人が採用したものだけを本番の生産予定・在庫予定・原料予定に反映する
5. 手動入力値と自動算出値を必ず分けて持つ
6. 計算処理は「再実行できる」「途中で失敗しても戻せる」設計にする

文字起こしでも、生成候補として「この日に作るべき」という数量を出すイメージが話されており、最終的には受注・出荷・業務管理システムと連結して自動化する流れです。

---

# 推奨アーキテクチャ

既存システムに以下の層を追加するイメージがよいです。

```text
既存画面・既存DB
   ↓
追加マスタ層
   商品 / 原料 / BOM / 作業場所 / シフト / 能力 / リードタイム
   ↓
計算エンジン層
   需要予測 / 月間生産必要数 / 日別割当 / 原料所要量 / 在庫推移
   ↓
生成候補層
   生産候補 / 原料不足候補 / 発注候補 / 残業候補
   ↓
承認・反映層
   採用 / 修正 / 却下 / 本予定化 / 在庫予定反映
   ↓
実績反映層
   日報 / 実績数量 / 差分再計算 / 能力値更新
```

この構造にしておくと、今は手動で入力している部分を残しながら、後から受注連携・日報連携・AI予測を追加しやすくなります。

# Phase 0：既存システム調査・保護レイヤー作成

## 目的

まず、既存システムのどこに追加すれば壊れないかを確認します。バイブコーディングでは、ここを飛ばすと後で破綻しやすいです。

## 設計

確認すべきものは以下です。

| 確認対象   | 見ること                             |
| ------ | -------------------------------- |
| 既存DB   | 商品、在庫、受注、出荷、生産予定、日報に相当するテーブルがあるか |
| 既存API  | 生産予定・在庫更新・受注取得・日報登録のAPIがあるか      |
| 既存画面   | 月間予定、日別予定、在庫一覧、生成候補の画面があるか       |
| 既存ロジック | すでに在庫計算・スケジュール割当・原料算出があるか        |
| 権限     | 現場入力者、管理者、承認者の区分があるか             |
| 連携     | 業務管理システムとの連携口があるか                |

## バイブコーディング指示書

```text
既存システムを調査してください。
目的は、既存機能を壊さずに、生産計画・在庫・原料発注・日報連携機能を追加することです。

以下を洗い出してください。

1. 商品、在庫、生産予定、受注、出荷、日報に関係する既存テーブル
2. それぞれの主キー、外部キー、更新箇所
3. 生産予定や在庫を更新している既存API
4. 既存画面で流用できる画面
5. 新規追加すべきテーブル
6. 既存テーブルに追加すべきカラム
7. 既存処理に影響が出る箇所
8. テストが必要な箇所

既存コードはまだ変更せず、調査結果と変更案だけを出してください。
```

## 直列処理が必要な箇所

| 処理                     | 理由                     |
| ---------------------- | ---------------------- |
| 既存DB確認 → 追加DB設計        | 既存構造を見ずに設計すると重複・破壊が起きる |
| 既存在庫更新処理確認 → 新しい在庫予定設計 | 在庫の二重計上を避けるため          |
| 既存生産予定確認 → 生成候補設計      | 既存予定と候補の区別が必要          |

## 並列処理できる箇所

| 作業         | 担当を分けられる理由 |
| ---------- | ---------- |
| 既存画面調査     | DB調査と並行可能  |
| 既存API調査    | 画面調査と並行可能  |
| 業務フロー整理    | コード調査と並行可能 |
| テストケース洗い出し | 調査と並行可能    |

# Phase 2：在庫台帳・予定在庫・実在庫の分離

## 目的

既存システムに在庫がある場合でも、今後は以下を分けて管理する必要があります。

| 種類     | 意味             |
| ------ | -------------- |
| 実在庫    | 現時点で実際にある数量    |
| 出荷予定   | これから減る予定の数量    |
| 生産予定   | これから増える予定の数量   |
| 原料使用予定 | これから減る予定の原材料   |
| 理論在庫   | 予定を全部反映した将来在庫  |
| 確定在庫   | 日報・出荷実績を反映した在庫 |

ここを分けないと、「予定を組んだだけなのに在庫が減る」「日報承認前に実在庫が変わる」などの問題が起きます。

## 設計

```text
inventory_ledger
- id
- item_type
  - PRODUCT
  - MATERIAL
- item_id
- movement_type
  - CURRENT_STOCK
  - PLANNED_PRODUCTION_IN
  - ACTUAL_PRODUCTION_IN
  - PLANNED_SHIPMENT_OUT
  - ACTUAL_SHIPMENT_OUT
  - PLANNED_MATERIAL_USE
  - ACTUAL_MATERIAL_USE
  - ADJUSTMENT
- qty
- movement_date
- source_type
  - ORDER
  - SHIPMENT
  - PRODUCTION_PLAN
  - DAILY_REPORT
  - PURCHASE_ORDER
  - MANUAL
- source_id
- status
  - PLANNED
  - CONFIRMED
  - CANCELLED
- created_at
```

## バイブコーディング指示書

```text
在庫管理を、実在庫と予定在庫に分離してください。

要件:
1. 在庫の増減はinventory_ledgerに記録する
2. 既存の在庫数を直接更新する処理がある場合は、互換性を残しながらledger方式に寄せる
3. 生産予定、出荷予定、原料使用予定はPLANNEDとして登録する
4. 日報承認、出荷実績、入荷実績はCONFIRMEDとして登録する
5. 同じsource_type + source_idで二重登録されないようにする
6. 指定日までの理論在庫を計算する関数を作る
7. 商品在庫と原材料在庫を同じ仕組みで扱えるようにする
8. 既存画面には影響を出さず、新しい在庫推移APIを追加する
```

## 直列処理が必要な箇所

```text
受注・出荷予定取得
  ↓
製品在庫予定を減算
  ↓
不足日を検出
  ↓
生産必要数を算出
  ↓
生産予定を作成
  ↓
製品在庫予定を増加
  ↓
原材料使用予定を減算
```

この順番は崩せません。
出荷予定が分からない状態で生産必要数を出すと、必要数量がズレます。

## 並列処理できる箇所

| 処理           | 理由             |
| ------------ | -------------- |
| 商品別の在庫推移計算   | 商品ごとに独立している    |
| 原材料別の在庫推移計算  | 原材料ごとに独立している   |
| 画面表示用の集計     | ledger確定後なら並列可 |
| CSV取込バリデーション | DB反映前なら並列可     |

# Phase 3：月間生産計画・需要予測

## 目的

月間で「何を何ケース作るべきか」を出します。

このフェーズでは、いきなり完全自動にせず、以下の4つを分けます。

```text
自動予測数量
+ 営業予測数量
+ スポット数量
+ 手動補正数量
= 最終月間生産予定数量
```

新商品は営業側から数量が来ること、分からない商品は受注生産になること、スポットは予測に加算することが話されています。

## 設計

```text
monthly_production_plans
- id
- target_month
- product_id
- base_forecast_qty
- sales_forecast_qty
- spot_qty
- special_order_qty
- manual_adjustment_qty
- final_plan_qty
- forecast_method
- status
  - DRAFT
  - CALCULATED
  - MANUAL_ADJUSTED
  - APPROVED
- calculation_run_id
```

```text
monthly_forecast_sources
- id
- monthly_plan_id
- source_type
  - LAST_YEAR
  - YEAR_RATIO
  - SALES_INPUT
  - SPOT
  - SPECIAL_ORDER
  - MANUAL
- source_qty
- note
```

## 予測ロジック

基本ロジックは以下です。

```text
対象月の前年実績 × 前々月の前年比率 = 対象月の予測数量
```

例：

```text
前年4月実績: 1000ケース
今年4月実績: 900ケース
前年比率: 90%

前年5月実績: 700ケース
今年5月予測: 700 × 90% = 630ケース
```

文字起こしでも、前年同月だけではなく、直近月の落ち方・増え方を反映して予測する話が出ています。また、前月確定を待つと原材料リードタイムに間に合わないため、前々月を使う方がよいという話も出ています。

## 特殊案件

チラシ掲載系、文字起こしでは「請求」と聞こえる箇所は、通常の前年実績から除外して別枠にします。掲載されるかどうかで注文有無が変わるため、平均に混ぜると予測がブレるという話が出ています。

```text
special_demand_events
- id
- product_id
- customer_id
- target_month
- qty
- event_type
  - FLYER
  - SPECIAL_CUSTOMER
  - CAMPAIGN
- include_in_normal_forecast
  - false
- status
```

## バイブコーディング指示書

```text
月間生産計画と需要予測機能を追加してください。

要件:
1. 商品ごと、月ごとに月間生産計画を作成できる
2. 自動予測数量、営業予測数量、スポット数量、特殊案件数量、手動補正数量を分けて保存する
3. final_plan_qtyは各数量の合計で算出する
4. 予測方式は商品ごとに切り替え可能にする
5. 在庫生産品のみ自動予測対象にする
6. 受注生産品は自動予測しない
7. 新商品は営業予測数量を優先する
8. 前年同月実績 × 前々月前年比率で予測できる関数を作る
9. チラシ・特殊顧客案件は通常実績から除外できるようにする
10. 規格変更商品はequivalence_groupで合算できるようにする
11. 計算結果の根拠をmonthly_forecast_sourcesに保存する
12. 手動補正しても、自動予測値は上書きしない
```

## 直列処理が必要な箇所

```text
前年実績取込
  ↓
商品統合ルール適用
  ↓
特殊案件除外
  ↓
前々月前年比率計算
  ↓
対象月予測数量計算
  ↓
営業予測・スポット加算
  ↓
手動補正
  ↓
月間生産計画承認
```

特に、**特殊案件除外と規格変更商品の統合は、予測計算より前**に必要です。

## 並列処理できる箇所

| 処理        | 理由             |
| --------- | -------------- |
| 商品別の予測計算  | 商品ごとに独立        |
| 営業予測入力UI  | 予測エンジン実装と並行可   |
| 特殊案件管理UI  | 商品統合マスタと並行可    |
| 前年実績CSV取込 | 画面実装と並行可       |
| 予測根拠表示    | 計算API完成後に並行実装可 |

# Phase 4：月間予定から日別生産スケジュールへの自動割り振り

## 目的

月間生産計画を、日別・作業場所別・時間別に割り振ります。

文字起こしでは、1部屋しかない場合は同時に2つできない、100件作れるなら今日はAを100件、次の日にBを100件のように自動振り分けしたい、という話が出ています。シフト、作業場所、日報で現在数量が出ていることが入力として必要とも整理されています。

## 設計

```text
production_plan_runs
- id
- target_month
- run_type
  - AUTO
  - MANUAL_RECALC
  - DAILY_REPORT_RECALC
- status
  - RUNNING
  - COMPLETED
  - FAILED
- created_by
- created_at
```

```text
production_schedule_candidates
- id
- run_id
- scenario_name
- product_id
- work_date
- work_center_id
- planned_qty
- required_hours
- worker_count
- start_time
- end_time
- overtime_minutes
- status
  - CANDIDATE
  - ACCEPTED
  - REJECTED
  - MODIFIED
- warning_status
```

```text
production_schedule_warnings
- id
- candidate_id
- warning_type
  - CAPACITY_OVER
  - WORK_CENTER_CONFLICT
  - MATERIAL_SHORTAGE
  - STOCK_SHORTAGE
  - OVERTIME_REQUIRED
  - SHIFT_MISSING
- message

```

## スケジューリングの基本ロジック

```text
月間必要数量
  ↓
出荷日・在庫切れ見込み日を確認
  ↓
作るべき期限を決める
  ↓
商品ごとの1日上限・1時間あたり能力を取得
  ↓
シフト・休憩・作業場所の空き枠を取得
  ↓
日別に割り振る
  ↓
入りきらなければ警告
  ↓
残業あり・なしの複数候補を作る
```

## 候補パターン

最低限、以下の3パターンを出すとよいです。

| 候補       | 内容           |
| -------- | ------------ |
| 通常勤務内プラン | 17時終了、残業なし   |
| 残業許可プラン  | 18時までなど残業あり  |
| 前倒しプラン   | 空き日に前倒しして平準化 |

文字起こしでも、パターンを出して人間が判断すること、残業するのか5時で閉めるのかを選ぶ話が出ています。

## バイブコーディング指示書

```text
月間生産計画から、日別・作業場所別の生産スケジュール候補を自動生成してください。

要件:
1. APPROVEDのmonthly_production_plansを対象にする
2. 商品ごとの月間数量を、作業日ごとに分割する
3. 1日あたり生産上限、1時間あたり生産能力を考慮する
4. work_centerが同時稼働不可の場合、同じ時間帯に複数予定を入れない
5. シフト、休憩、残業可否を考慮する
6. 17時終了プラン、18時終了プラン、前倒しプランを生成する
7. 予定が入りきらない場合はwarningを出す
8. 候補は本予定に直接反映せず、production_schedule_candidatesに保存する
9. ユーザーが候補を採用したときだけ本予定に反映する
10. 同じrun_idで再計算できるようにする
11. 計算途中で失敗しても既存予定を壊さない
```

## 直列処理が必要な箇所

```text
月間生産計画承認
  ↓
対象月の営業日・シフト取得
  ↓
作業場所の稼働枠作成
  ↓
商品ごとの必要数量計算
  ↓
優先順位決定
  ↓
日別割当
  ↓
作業場所衝突チェック
  ↓
能力超過チェック
  ↓
候補保存
  ↓
人が採用
  ↓
本予定反映
```

特に、**候補保存までは自動、本予定反映は人の採用後**にするべきです。

```text
  ↓

  ↓
```


文字起こしでは、予定3000に対して実績2500、逆に3500できた場合、その実数に切り替わって次に作るべき数量が出る流れが話されています。

## バイブコーディング指示書

```text
日報入力、承認、実績反映、再計算の機能を追加してください。

要件:
1. タブレットで入力しやすい日報画面を作る
2. 日付、商品、作業場所、開始時刻、終了時刻、人数、生産数量、不良数、備考を入力できる
3. 日報は入力直後に在庫へ反映せず、APPROVED後に反映する
4. 承認時にACTUAL_PRODUCTION_INとして製品在庫を増やす
5. 承認時にACTUAL_MATERIAL_USEとして原材料在庫を減らす
6. 対応する生産予定との差分を計算する
7. 不足分または超過分を翌日以降のスケジュール再計算に渡す
8. 実績からqty_per_hourを計算し、capacity_observationsに保存する
9. 一定件数以上の日報が溜まったら中央値でproduction_capacitiesを更新できるようにする
10. ただしlocked=trueの能力値は自動更新しない
```

## 直列処理が必要な箇所

```text

  ↓

  ↓
管理者承認
  ↓
実績在庫反映
  ↓
予定差分計算
  ↓
翌日以降再計算
  ↓
能力値更新
```

**承認前に在庫や能力値を更新してはいけません。**
日報が間違っていた場合に、在庫・予定・能力値が全部ズレます。

* 取込後に在庫・生産候補を再計算できる

## Phase 8 完了条件

* 複数シナリオを比較できる
* 推奨候補が出る
* なぜその候補なのか説明できる
* 人が承認するまで本予定化されない
* 受注変更・日報実績で再計算できる

# 最初に実装すべき最小MVP

すでに既存システムがある前提なら、最初のMVPはここまででよいです。

```text
1. 商品マスタに生産区分を追加
2. 原材料・BOM・リードタイムを追加
3. 月間生産計画を手動入力できる
4. 月間数量を日別に自動割り振る
5. 生成候補として保存する
6. 候補を採用できる
7. 採用した予定から原材料使用予定を出す
8. 原材料不足と発注期限アラートを出す
```

このMVPができれば、文字起こしで一番強く求められていた、

```text
月間でこれだけ作る
↓
日別に割り振る
↓
原料が足りるか分かる
↓
足りなければ発注候補が出る
↓
人が確認するだけ
```

という流れに入れます。

# 最終的な開発指示のまとめ

開発者、またはAIコーディングツールには、最初にこの方針を渡すとよいです。

```text
既存の在庫・生産管理システムに、月間生産計画、日別スケジューリング、原材料発注アラート、日報実績反映を段階的に追加する。

重要方針:
- 既存機能を壊さない
- 自動計算結果はまず候補として保存する
- 人が承認するまで本予定には反映しない
- 手動入力値と自動計算値を分けて保存する
- 予定と実績を分ける
- 在庫はledger形式で管理する
- 再計算可能な設計にする
- 受注、出荷、日報、シフト、原料、BOMを最終的に連動させる
- 直列処理が必要な箇所には排他制御を入れる
- 商品別、原料別、シナリオ別の計算は並列化できるようにする

実装順:
1. 既存調査
2. マスタ追加
3. 在庫台帳
4. 月間計画
5. 日別スケジューラ
6. 原料使用予定・発注アラート
7. 日報実績反映
8. 業務管理連携
9. 高度化
```

この順番なら、今あるシステムを活かしながら、途中段階でも使える形にできます。
一番避けるべきなのは、最初から「完全自動」を作ろうとして、手動運用もできない・自動も不安定という中途半端な状態になることです。
