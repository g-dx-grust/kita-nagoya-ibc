# 18. 実装フェーズ計画（並列／直列の区別つき）

このドキュメントは [docs/文字起こし要約.md](文字起こし要約.md) と [docs/gpt新規実装.md](gpt新規実装.md) を統合し、本リポジトリ `CLAUDE.md` の方針に揃えた実装ロードマップである。

---

## 0. 前提と読み方

### 適用する大方針（CLAUDE.md 準拠）

- **初期MVPでは生産計画の自動生成は行わない**。生産予定は人が登録する。
- 登録済みの生産予定から、所要時間・原料/資材使用量・在庫不足・発注候補・原価・手間賃・日報・請求用データを連動させる。
- 自動計算結果は本データに直接反映せず、**生成候補 → 人の採用 → 本予定化** の流れにする。
- 手動入力値と自動算出値、`planned_*` と `actual_*` は必ず分けて持つ。
- 発注済み未入荷は確定在庫と別扱い。外注/AX は請求対象フラグで分ける。

### gpt新規実装.md との対応

gpt新規実装.md は Phase 0〜8 の9段構成だが、本リポジトリは「製品在庫からの自動生産計画」を Phase 6（後ろ）に置く方針のため、**Phase 3（月間生産計画・需要予測）と Phase 4（日別自動割当）は本計画では後ろにずらす**。MVP は手動入力した生産予定を起点に下流を回す形で確定する。

### 表記ルール

- ▶ **直列必須**：前ステップが完了しないと次に進めない。
- ‖ **並列可**：同じフェーズ内、または別フェーズ間で同時並行に進められる。
- 各フェーズの末尾に「完了条件（受け入れ基準）」と「次フェーズに渡す前提データ」を明記する。

## 1. フェーズ全体マップ

```
Phase 0  既存調査・保護レイヤー
   │
   ▼
Phase 1  マスタ・DB拡張（商品/原料/資材/BOM/作業場所/能力/シフト/リードタイム）
   │
   ▼
Phase 2  在庫台帳（予定在庫 / 確定在庫 / 未確定発注の分離）
   │
   ▼
Phase 3  手動生産予定 MVP（CLAUDE.md の MVP 受け入れ基準ライン）
   │      └─ ここで「現場で運用開始できる最小形」が成立する
   ▼
Phase 4  原料・資材使用予定 / リードタイム発注アラート / 発注書自動生成
   │
   ▼
Phase 5  日報電子化・実績反映・予定差分による再計算
   │
   ▼
Phase 6  請求 / 売上伝票 / 手間賃 CSV・Excel 出力
   │
   ▼
Phase 7  業務管理システム連携（受注・出荷・前年実績の取込）
   │
   ▼
Phase 8  月間需要予測・日別自動割当・複数シナリオ（自動生成解禁）
   │      └─ 数か月先までのローリング予測、仮シフト将来月計算を含む
   ▼

   │
   ▼
```

- **Phase 4〜6** で在庫・発注・請求まで一気通貫になる。
- **Phase 7〜8** で受注連携と自動計画が乗り、文字起こしの「最終形」に到達する。
- **Phase 9** で文字起こし §優先度C-27（AI による異常検知・提案）まで実装する。
- **アラート／ダッシュボード／実績分析** は §19 に横断機能として集約。

## 2. Phase 0：既存調査・保護レイヤー

### 目的

既存システム（既存DB／既存画面／既存API）に追加して壊さないために、影響範囲とインタフェース境界を確定する。

### 直列タスク

| # | 内容 | 出力物 |
|---|---|---|
| ▶ 0-1 | 既存DBスキーマ調査（商品・在庫・受注・出荷・日報相当の有無） | テーブル一覧と用途メモ |
| ▶ 0-2 | 既存API・既存ロジック調査（在庫更新／予定登録／日報登録など） | API一覧と影響範囲 |
| ▶ 0-3 | 既存と新規の境界線確定（既存テーブル拡張 vs 新規テーブル分離） | 設計方針メモ |

### 並列可タスク（0-1〜0-3 と並行可）

| 作業 | 並列にできる理由 |
|---|---|
| ‖ 既存画面棚卸し | DB調査と独立 |
| ‖ 業務フロー整理（オペレーション側） | コード調査と独立 |
| ‖ テストケース洗い出し | 調査結果は後で当てる |
| ‖ Wi-Fi／タブレット現地調査（Phase 5 前提） | システム実装と完全独立 |

### 完了条件

- 「既存を壊さず追加できる場所」が画面・API・テーブルレベルで列挙されている。
- Phase 1 で新規追加するテーブル一覧の初版がある。

### 次フェーズへの引き継ぎ

- 既存 products/orders/shipments 相当テーブルの主キーと結合キー。
- 既存在庫更新処理がある場合、その入口関数・呼び出し元。

## 3. Phase 1：マスタ・DB拡張

### 目的

下流のすべての計算（所要時間・原料消費・在庫推移・発注期限・手間賃）が依存するマスタを揃える。

### 直列タスク（依存順）

```
▶ 1-1 商品マスタ拡張（生産区分・予測方式・規格情報）
   │
   ▼
▶ 1-2 原材料マスタ・資材マスタ（在庫・リードタイム・発注単位・安全在庫）
   │
   ▼
▶ 1-3 BOM（商品 → 原料・資材の使用量、ロス率、有効期間）
   │       ※ 商品と原料の両方が無いと作れない
   ▼
▶ 1-4 作業場所マスタ（ROOM/LINE/MACHINE、同時稼働可否）
   │
   ▼
▶ 1-5 生産能力マスタ（商品×作業場所×人数×1時間あたり生産量、source_type=MANUAL初期）
   │       ※ 商品と作業場所の両方が無いと作れない
   ▼
▶ 1-6 シフト・休憩・カレンダーマスタ（勤務時間、休憩、残業可否、土曜稼働）
   │
   ▼
▶ 1-7 商品統合（規格変更）マスタ・特殊案件マスタ
        ※ 予測フェーズ（Phase 8）で本格利用。Phase 1 では枠だけ。
```

### 並列可タスク

| グループA | グループB | 並列可の条件 |
|---|---|---|
| ‖ 商品マスタ CRUD UI | ‖ 原材料マスタ CRUD UI | DB設計が 1-1, 1-2 で固まっていれば独立 |
| ‖ BOM 編集 UI | ‖ 作業場所 CRUD UI | テーブル定義が確定済 |
| ‖ シフト UI | ‖ 休憩マスタ UI | 勤務時間の正規化方針が決まっている |
| ‖ CSV インポート（マスタ系） | ‖ 通常の CRUD 実装 | マスタテーブル定義が固まっている |
| ‖ Seed データ作成 | ‖ 画面実装 | スキーマ確定後ならいつでも |

### 共通要件（全マスタ）

- `active`, `valid_from`, `valid_to` を持たせ、改廃に対応する。
- 商品名・商品番号・原料名・資材名は正式名称をキーにする（曖昧な手入力名称をキーにしない）。
- 部屋名・外注先名は固定値にせず、マスタで追加・変更できる構造。

### 完了条件

- CLAUDE.md の受け入れ基準のうち「商品マスタに 1時間1人あたり生産量、レシピ/BOM、手間賃単価を設定できる」を満たす。
- 全マスタについて CRUD と CSV インポートが動作する。

### 次フェーズへの引き継ぎ

- 商品ID・原料ID・作業場所ID・能力レコードIDが Phase 2 以降の外部キーとして利用可能。

## 4. Phase 2：在庫台帳の分離（予定／確定／未確定発注）

### 目的

「予定を組んだだけで在庫が減る」「未確定の入荷を確定在庫に混ぜる」事故を起こさない仕組みに作り変える。

### 直列タスク

```
▶ 2-1 inventory_ledger テーブル設計
        item_type / movement_type / source_type / source_id / status(PLANNED|CONFIRMED|CANCELLED)
   │
   ▼
▶ 2-2 在庫増減を全て ledger 経由にする抽象化（既存直接更新は互換ラッパー越し）
   │
   ▼
▶ 2-3 二重登録防止（source_type + source_id のユニーク制約）
   │
   ▼
▶ 2-4 指定日までの理論在庫計算関数（商品・原材料共通）
   │
   ▼
▶ 2-5 未確定発注（発注済み未入荷）の区分表示
```

### 並列可タスク

| 作業 | 並列にできる理由 |
|---|---|
| ‖ 商品在庫推移計算 | 商品IDごとに独立 |
| ‖ 原材料在庫推移計算 | 原料IDごとに独立 |
| ‖ Excel風 在庫一覧 UI | ledger API が固まっていれば独立 |
| ‖ CSV 取込のバリデーション（在庫初期値） | DB反映前なら自由に書ける |

### 完了条件

- 実在庫・予定在庫・未確定発注が別カラムまたは別タグで判別できる。
- 同じ source からの二重反映が物理的に発生しない（ユニーク制約 or 冪等処理）。
- 任意日付の理論在庫を関数1本で取得できる。

### 次フェーズへの引き継ぎ

- `inventory_ledger.movement_type` に `PLANNED_PRODUCTION_IN` / `PLANNED_MATERIAL_USE` を発行する権利が Phase 3 に渡る。

## 5. Phase 3：手動生産予定 MVP（CLAUDE.md の MVP ライン）

### 目的

**CLAUDE.md の受け入れ基準の本丸**。人が生産予定を入れると、所要時間・あふれ・原料使用量・在庫不足が自動で出るところまで作る。

### 直列タスク

```
▶ 3-1 production_schedules テーブル（商品・数量・人数・開始時刻・作業場所・状態）
   │
   ▼
▶ 3-2 所要時間計算サービス
        end_time = start_time + qty / (qty_per_hour_per_person × worker_count) + 休憩
   │
   ▼
▶ 3-3 時間枠制約の判定（「この時間枠で何個作れる／何個あふれる」を返す）
   │
   ▼
▶ 3-4 BOM 展開 → 原料/資材の planned 使用量を inventory_ledger に発行
   │
   ▼
▶ 3-5 製品在庫の planned 増加を inventory_ledger に発行
   │
   ▼
▶ 3-6 在庫不足・マイナス・未確定入荷の判別表示（画面）
```

### 並列可タスク

| 作業A | 作業B | 条件 |
|---|---|---|
| ‖ 予定登録 UI | ‖ 予定一覧 UI | テーブル定義が 3-1 で固まっている |
| ‖ 計算ユニットテスト（所要時間） | ‖ 計算ユニットテスト（時間枠あふれ） | サービス境界が決まっている |
| ‖ 在庫不足画面 | ‖ 予定登録画面 | 在庫推移APIが固まっている |
| ‖ サンプルデータ用 Seed | ‖ ロジック実装 | 入力スキーマが確定 |

### 完了条件（= CLAUDE.md の MVP 受け入れ基準）

- 商品マスターに 1時間1人あたり生産量、BOM、手間賃単価を設定できる。
- 生産予定に商品・数量・人数・開始時刻を入れると終了時刻が出る。
- 時間枠を指定すると、その時間内で作れる数量とあふれ数量が出る。
- 生産予定から原料/資材の予定使用量が出る。
- 在庫不足・マイナス・未確定入荷が画面で判別できる。

### 次フェーズへの引き継ぎ

- 採用済み（ACCEPTED）の `production_schedules.id` 一覧が Phase 4 の入力。
- 監査ログ：在庫を減らす処理・予定確定処理は監査ログを残す（CLAUDE.md 要件）。

## 6. Phase 4：原料・資材の発注アラート

### 目的

予定を組んだ時点で原料・資材の使用予定を立て、リードタイムを引いて「いつまでに発注すべきか」を逆算する。

### 直列タスク

```
▶ 4-1 material_requirements（生産予定×BOM の planned 使用量を行レベルで保存）
   │
   ▼
▶ 4-2 原料/資材の在庫推移計算（Phase 2 の理論在庫関数を再利用）
   │
   ▼
▶ 4-3 不足検出（安全在庫割れ／マイナス）
   │
   ▼
▶ 4-4 リードタイム逆算 → required_order_date 算出
   │
   ▼
▶ 4-5 発注候補（purchase_order_candidates）の生成と緊急度判定
   │
   ▼
▶ 4-6 候補 → 人の承認 → 本発注化（監査ログ必須）
   │
   ▼
▶ 4-7 発注書テンプレート → PDF/Excel 自動生成（仕入先別、人は内容確認して送るだけ）
```

### 並列可タスク

| 作業 | 並列にできる理由 |
|---|---|
| ‖ 原材料ごとの推移計算 | material_id ごとに独立 |
| ‖ 商品ごとの BOM 展開 | product_id ごとに独立 |
| ‖ 発注候補一覧 UI | 計算ロジックと独立して進められる |
| ‖ 発注書 PDF/Excel 出力 | アラート画面と独立 |
| ‖ 仕入先マスタ画面 | 発注計算と独立 |
| ‖ メール添付テンプレート（任意送信） | 発注書フォーマット確定後に独立 |

### 完了条件

- 採用済み生産予定から原料/資材の予定使用量が出る。
- 在庫切れ日と「いつ発注すべきか」が表示される。
- 発注期限を過ぎている場合は CRITICAL アラートが出る。
- 発注済み未入荷は確定在庫と区別される。
- 承認された発注候補から発注書 PDF/Excel が自動生成され、人は確認して送付するだけになる（文字起こし §L 要件）。

## 7. Phase 5：日報電子化・実績反映・再計算

### 目的

紙の日報をタブレット入力に置き換え、承認後に **planned → actual** へ振り替えて在庫・原価・能力値を更新する。

### 直列タスク

```
▶ 5-1 daily_reports / daily_report_lines テーブル設計
   │
   ▼
▶ 5-2 タブレット入力 UI（日付・商品・作業場所・開始/終了・人数・実績数量・不良数・備考）
   │
   ▼
▶ 5-3 提出 → 管理者承認フロー（承認前は在庫・能力値に絶対反映しない）
   │
   ▼
▶ 5-4 承認時、ACTUAL_PRODUCTION_IN / ACTUAL_MATERIAL_USE を inventory_ledger に発行
   │
   ▼
▶ 5-5 対応する生産予定との差分計算（実績 < 予定 → 残数を翌日以降に振替 等）
   │
   ▼
▶ 5-6 capacity_observations へ実績蓄積 → 一定数溜まったら中央値で能力値更新
        ※ ただし production_capacities.locked = true は自動更新しない
```

### 並列可タスク

| 作業A | 作業B | 条件 |
|---|---|---|
| ‖ タブレット入力画面 | ‖ 承認画面 | スキーマ確定 |
| ‖ 能力値中央値ジョブ | ‖ 在庫反映処理 | 承認イベント仕様確定 |
| ‖ 実績レポート（予定対比） | ‖ 日報登録機能 | 集計APIが固まっていれば独立 |
| ‖ Wi-Fi／タブレット端末配備 | ‖ システム実装 | 完全独立（Phase 0 から走らせて可） |

### 完了条件（CLAUDE.md より）

- 日報実績を入れると予定値ではなく実績値で在庫・原価が再計算される。
- 日報確定は監査ログを残す。
- 承認前の日報が在庫・能力値・予定に影響しない。

## 8. Phase 6：請求・売上伝票・手間賃 CSV/Excel 出力

### 目的

実績データを CSV/Excel で出して、既存の業務管理／経理ワークフローに渡せる状態にする。

```

   │
   ▼
▶ 6-4 売上伝票／請求 CSV・Excel 出力（フォーマットは要確認）

```

### 並列可タスク

| 作業 | 並列にできる理由 |
|---|---|
| ‖ 手間賃レポート画面 | ‖ 原価レポート画面 |
| ‖ Excel テンプレート整備 | ‖ 集計ロジック実装 |
| ‖ 請求対象フラグ UI | ‖ 集計クエリ実装 |

### 完了条件

- 請求/売上伝票用 CSV または Excel を出力できる。

### 並列可タスク

- 受注・出荷を外部データから取り込める。
- 同じ external_order_id は二重取込されない。
- 取込エラーが画面で確認・修正できる。

## 10. Phase 8：需要予測・日別自動割当・複数シナリオ

### 目的

Phase 3 では人が登録していた月間予定・日別予定を、システムが「候補」として提案する状態に進化させる。**ここに来て初めて自動生成を解禁する**（CLAUDE.md：最終形）。

### 直列タスク

```
▶ 8-1 monthly_production_plans / monthly_forecast_sources
   │
   ▼
▶ 8-2 前年実績取込（Phase 7 と連動）
   │
   ▼
▶ 8-3 商品統合（規格変更）グループ適用
   │
   ▼
▶ 8-4 特殊案件（チラシ等）の通常実績からの除外
   │
   ▼
▶ 8-5 需要予測ロジック（前年同月 × 前々月の前年比率）
   │
   ▼
▶ 8-6 営業予測・スポット・手動補正の加算 → final_plan_qty
   │
   ▼
▶ 8-7 月間予定 → 日別生産候補（production_schedule_candidates）の自動生成
        作業場所衝突・能力超過・原料不足・残業要否の判定付き
   │
   ▼
▶ 8-8 複数シナリオ（通常 / 残業 / 前倒し）出し
   │
   ▼
▶ 8-9 数か月先までのローリング予測・原材料不足予測（rolling_forecast_horizon = 例:3〜6か月）
   │       ※ 文字起こし §優先度C-23
   ▼
▶ 8-10 仮シフト（標準シフト or 前月コピー）による将来月の能力計算
   │       ※ 文字起こし §優先度C-24
   ▼
▶ 8-11 人が候補を採用 → Phase 3 の本予定として反映
```

### 並列可タスク

| 作業 | 並列にできる理由 |
|---|---|
| ‖ 商品別予測計算 | product_id ごとに独立 |
| ‖ シナリオ A（通常）／ B（残業）／ C（前倒し） | シナリオ間で独立 |
| ‖ 営業予測入力 UI | ‖ 予測エンジン実装 |

| ‖ 仮シフト生成（標準パターン適用） | 将来月の能力計算と並行 |

### 完了条件

- 月間予定が複数の根拠（自動／営業／スポット／手動）に分解されて保存される。
- 日別候補が複数シナリオ並んで出る。
- 採用までは本予定に反映されない。
- 受注変更・日報差分・在庫差分で再計算ジョブが走る。
- 数か月先までの生産計画／原材料不足予測が出せる。
- 仮シフトで将来月の能力計算ができる。

## 11. Phase 9：AI高度化・異常検知・自動再計算

### 目的

文字起こし §優先度C-27（AI による異常検知・提案）と、gpt新規実装 §Phase 8（自動再計算・推奨理由表示）を実装する。**LLM に投げるのではなく、ルールベース + 履歴データ + 統計判定 が基本**。LLM はあくまで説明文生成や自由記述要約などに限定使用。

### 直列タスク

```
▶ 9-1 異常検知ルールエンジン
        - 予測 vs 実績の急変（標準偏差 n倍など）
        - 能力値の急変（中央値の前後比較）
        - 原料消費の急増
        - 在庫マイナス頻発
   │
   ▼
▶ 9-2 calculation_reason / recommendation_reason の保存と表示
        各候補に「なぜこの数量／この日／この場所か」を構造化メモで残す
   │
   ▼
▶ 9-3 自動再計算ジョブの統合
        - 受注変更検知 → Phase 7→8 連鎖
        - 日報差分検知 → Phase 5→8 連鎖
        - 在庫調整検知 → Phase 2→4 連鎖
        ジョブキュー化、排他、リトライ、失敗時ロールバック
   │
   ▼
▶ 9-4 シナリオ推奨スコアリング（在庫不足／原料不足／残業／場所衝突の重み付き）
        最良候補に "recommended" タグを付ける（自動採用はしない）
   │
   ▼
▶ 9-5 LLM 説明文生成（任意）
        "残業3時間で出荷遅延を回避するため A 案を推奨" のような自然文を生成
```

### 並列可タスク

| 作業 | 並列にできる理由 |
|---|---|
| ‖ 異常検知ルール各種 | 検知種別ごとに独立 |
| ‖ 再計算ジョブ × トリガー別 | トリガーごとに独立 |
| ‖ 推奨スコアリング | 候補生成完了後に独立 |
| ‖ 説明文 UI | スコアリング API 完了後に独立 |

### 完了条件

- 予測と実績、能力値、在庫の異常が検知され画面に出る。
- 各候補に推奨理由が構造化で残る。
- 受注・日報・在庫の変更で再計算ジョブが自動起動する。
- 推奨候補が示されるが、自動採用はしない（CLAUDE.md：人が承認するまで本予定化しない）。

### 注意

- LLM を計算ロジック本体に組み込まない。理由：説明性・再現性が落ちる、コスト、Lark から開発に切り替えた経緯（文字起こし §6）。

## 12. 排他制御（全フェーズ共通）

下記操作は同時実行で破綻するため、`calculation_locks` か DB トランザクションでロックする。

| 対象 | 理由 |
|---|---|
| 同じ月の生産計画再計算 | 候補が二重生成される |
| 同じ生産予定の採用処理 | 複数人による二重採用 |
| 同じ日報の承認処理 | 二重在庫反映 |
| 同じ発注候補の承認処理 | 二重発注 |
| 同じ受注データ取込（external_order_id） | 二重出荷予定 |

lock_key 例：`monthly-plan:2026-07` / `production-schedule:2026-07` / `daily-report:12345` / `purchase-candidate:98765` / `import-run:business-orders-2026-07-01`

## 13. 実行時の直列処理パイプライン

開発作業の順序とは別に、**運用時（システム実行時）に直列で流れる処理パイプライン**は以下：

### パイプライン A：手動予定 → 原料発注（Phase 3〜4）

```
生産予定登録（人）
   ▼
所要時間・終了時刻計算
   ▼
BOM 展開 → 原料/資材 planned 使用量
   ▼
在庫推移計算
   ▼
不足検出 → 発注候補
```

### パイプライン B：日報承認 → 再計算（Phase 5）

```
日報入力 → 提出 → 承認（人）
   ▼
ACTUAL_* を ledger に書く
   ▼
予定との差分計算
   ▼
翌日以降の再振替
   ▼
能力値の中央値更新（locked=false のみ）
```

### パイプライン C：受注取込 → 再計算（Phase 7）

```
取込 → staging → バリデーション
   ▼
本テーブル反映
   ▼
出荷予定更新 → 製品在庫推移更新
   ▼
不足検出 → 生産候補再生成（Phase 8 がある場合）
```

### パイプライン D：自動候補生成（Phase 8）

```
月間計画確定
   ▼
シナリオごとに並列計算（通常／残業／前倒し）  ← ここだけ並列
   ▼
能力・場所・原料チェック
   ▼
候補保存（人が採用するまで本予定化しない）
```

## 19. 横断機能：アラート / ダッシュボード / 実績分析

これらは特定フェーズに閉じず、各フェーズの実装と並行して育てる **横断機能** として位置づける。基盤を Phase 1 と並行で立て、各フェーズが自分のイベントを通知する形にする。

### 19-1. アラート基盤（文字起こし要約.md §R 対応）

#### 設計

```
alerts
- id
- alert_type
- severity (INFO / WARNING / CRITICAL)
- subject_type, subject_id     ← 製品・原料・予定・日報など
- target_date
- message
- source_phase                  ← 発火元フェーズ
- status (OPEN / ACK / RESOLVED)
- created_at, resolved_at
```

#### 各フェーズが発火するアラート

| アラート種別 | 発火フェーズ | トリガー |
|---|---|---|
| 製品在庫不足 | Phase 2〜3 | 出荷予定 > 在庫＋生産予定 |
| 原材料不足 | Phase 4 | 安全在庫割れ／マイナス |
| 発注期限超過 | Phase 4 | required_order_date < today |
| 生産能力超過 | Phase 3 / Phase 8 | 必要時間 > シフト時間 |

| 予測異常 | Phase 9 | 前年比 or 標準偏差超過 |
| 未入力 | 全フェーズ | シフト／日報／在庫／能力値の null 検知 |
| 連携エラー | Phase 7 | 取込失敗・バリデーション失敗 |

#### 並列可

- 各アラート種別の判定ロジックは **互いに独立** ⇒ 完全並列開発可。
