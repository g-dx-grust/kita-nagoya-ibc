以下、2026年5月21日の文字起こしをもとに、**システムとして実装すべき内容**を要件定義レベルで洗い出します。文字起こし上は一部表現が崩れているため、「請求」など文脈上あいまいな語はそのまま注記しています。

## 1. システム全体のゴール

目指しているのは、**受注・出荷・在庫・日報・シフト・原材料を連動させ、月間の生産予定から日別・現場別の生産スケジュール、原材料発注までを自動計算するシステム**です。

最終形は、
**人が毎回計算して予定を組むのではなく、システムが候補を出し、人は確認・修正・承認するだけ**
という状態です。

文字起こしでは、月間生産量を入れたら、1日あたりの生産上限に応じて自動で日割りされること、最終的にはAIまたは自動計算で人の作業を減らしたいことが繰り返し話されています。 また、現時点で手動が残る部分と、連携後に自動化される部分を明確に分けて作ってほしい、という要望も出ています。

# 2. 実装すべき主要機能一覧

## A. 受注・出荷・業務管理システム連携

### 実装内容

既存の業務管理システムと連携し、以下のデータを自動取得できるようにする必要があります。

| 項目           | 内容                   |
| ------------ | -------------------- |
| 受注データ        | 受注が入ったら自動で取得する       |
| 出荷予定・出荷実績    | 受注に応じた出荷日・出荷数量を取得する  |
| 前年度実績        | 月間予測の元データとして読み込む     |
| 商品別の出荷推移     | 需要予測・在庫消費計算に使用する     |
| 既存の業務管理側の入力値 | 現場が今入力している数量・予定と連結する |

文字起こしでは、「受注は勝手に打たれる」「出荷のところも勝手に出る」「業務管理の向こうの受注と連結する」という話があり、最終的には既存の業務管理システムと今回の在庫・生産管理側を連結する前提です。

### 要件

* 受注情報を手入力せず、既存システムから取得する。
* 出荷予定をもとに、製品在庫の将来減少を計算する。
* 業務管理システムにある前年度データを読み込む。
* 連携前はCSV/Excelインポートでもよいが、最終的には自動連携にする。
* 連携できている項目、まだ手動入力が必要な項目を画面上で明示する。

## B. 月間生産予定の自動算出

### 実装内容

商品ごとに、**月間でどれだけ作るべきか**を自動算出する機能が必要です。

対象は大きく分けて以下です。

| 区分        | 内容                         |
| --------- | -------------------------- |
| 在庫生産品     | 過去実績や予測をもとに先に作る商品          |
| 受注生産品     | 受注が来てから作る商品                |
| 新商品       | 営業側から「何ケース用意してほしい」と予測が来る商品 |
| スポット案件    | 営業から追加で入る一時的な需要            |
| チラシ・特定注文系 | 前年実績ではなく、掲載有無・注文有無で別管理する商品 |

文字起こしでは、在庫生産品について「去年の実績」「その前の実績」をもとに月間生産量を決め、受注生産品は基本的に仕掛けない、という話が出ています。

## C. 需要予測ロジック

### 実装内容

単純に前年同月の数字を使うだけではなく、**直近の増減傾向を反映した予測**が必要です。

会話内で示された考え方は、概ね以下です。

> 前年同月実績 × 直近月の前年比率 = 今年の対象月の予測数量

例として、
前年4月が1,000ケース、今年4月が900ケースなら、前年比90%。
前年5月が700ケースなら、今年5月は700 × 90% = 630ケース、という考え方です。

### 要件

* 商品別・月別の前年実績を保持する。
* 直近月または前々月の実績から前年比率を計算する。
* リードタイム問題を避けるため、予測計算には**前月ではなく前々月実績を使う**ことを基本にする。
* 営業からの追加見込み・新規導入・スポット需要を加算できる。
* 当月中に予測より増減した場合は、現場側で手動調整できる。
* 予測値と手動補正値を分けて保持する。

前月確定を待つと、原料リードタイムに間に合わないため、前々月を使う方がよいという話も出ています。

## D. 新商品・受注生産品・営業予測の扱い

### 実装内容

新商品や実績がない商品は、過去実績から予測できません。そのため、営業側から入る見込み数量を登録し、それを生産予定に反映する必要があります。

文字起こしでは、新商品は営業側から「これだけ用意してくれ」と来る、分からない商品は受注生産扱いにする、という話があります。

### 要件

* 商品マスタに「在庫生産」「受注生産」「営業予測あり」「新商品」などの区分を持たせる。
* 新商品は前年実績ではなく、営業入力の予測数量を使う。
* 実績がない商品は、受注生産または手動予測登録にできる。
* 営業予測数量は月別・商品別に登録できる。
* 営業予測が変わった場合、再計算できる。

## E. チラシ・特定注文案件の別枠管理

### 実装内容

文字起こしでは「請求」と聞こえる箇所がありますが、文脈上は**チラシ掲載によって注文が発生する特定案件**のように見えます。これは前年実績に混ぜると予測がブレるため、通常の前年ベース予測から除外して、別枠管理する必要があります。

チラシに掲載されたら注文が来るが、掲載されなければ注文が来ないため、前年実績に含めると過大予測になる、という説明があります。

### 要件

* 特定顧客・特定チャネル・チラシ案件を通常実績から除外できる。
* 除外した案件は「今年ある／ない」を別枠で登録する。
* 注文が2か月前など早めに分かる案件は、別枠で月間予定に加算する。
* 通常予測用の実績と、特殊案件込みの実績を分けて管理する。
* 予測ロジックに「特殊案件除外フラグ」を入れる。

## F. 規格変更・グラム変更商品の統合

### 実装内容

商品規格が変わった場合、前年実績と今年実績で別商品として扱われてしまう可能性があります。たとえば70gと80g、18gと10gのような規格変更があった場合、同一または類似商品として合算すべきケースがあります。

文字起こしでは、グラム変更・規格変更があった商品について、似たようなものが2つある場合は合計値で見る、という話が出ています。

### 要件

* 商品マスタに「旧商品コード」「新商品コード」「同一扱いグループ」を持たせる。
* 規格変更前後の商品を、予測上は合算できる。
* ただし、単純に合算してはいけない商品もあるため、手動で紐付けを管理できるようにする。
* 予測計算時は、商品単体またはグループ合算を選択できる。
* 商品規格変更履歴を保持する。

## G. 月間予定から日別生産スケジュールへの自動割り振り

### 実装内容

月間で作る数量が決まったら、日別に生産予定を自動配分する必要があります。

文字起こしでは、1日60ケースしか作れない商品に600ケースの月間数量がある場合、10日に分けて割り振るようなイメージが話されています。

### 要件

* 月間生産必要数を日別に自動割り振りする。
* 商品ごとの1日生産上限、1時間あたり生産数を考慮する。
* 生産場所・部屋・ライン・機械の制約を考慮する。
* 同じ場所で同時に複数作業ができない制約を入れる。
* 出荷日・在庫残・製造リードタイムを考慮して、必要日までに作る。
* 予定が入りきらない場合はアラートを出す。
* 可能であれば複数の候補パターンを出し、人が選べるようにする。

## H. シフト・作業場所・休憩時間を考慮した生産能力計算

### 実装内容

生産予定は、単純な数量だけでなく、実際に働ける人員・時間・作業場所で計算する必要があります。

文字起こしでは、入力が必要な項目として「従業員のシフト」「作業場所」「最終日報で現在数量が出ていること」が挙がっています。また、休憩時間は合計75分、9時・15時などの休憩時間も話題に出ています。 

### 要件

* 従業員シフトを登録できる。
* 作業場所・部屋・ライン・機械の稼働可否を登録できる。
* 通常勤務時間、休憩時間、残業時間を設定できる。
* 17時終了パターン、18時まで残業パターンなどを比較できる。
* 土曜稼働も扱える。
* 将来月でシフトが未確定の場合は、仮シフト・標準シフトで計算できる。
* 人員数 × 作業時間 × 生産能力で、その日の生産可能量を算出する。

## I. 前倒し・後ろ倒し・残業判断のスケジューリング

### 実装内容

繁忙期には、通常時間内では予定が収まらないことがあります。その場合、前倒し、後ろ倒し、残業、別日の空き時間活用などを提案する機能が必要です。

文字起こしでは、「5時まで」「6時まで」「空白がある」「前倒しする」「繁忙期はギリギリを攻める」といった運用が説明されています。 

### 要件

* 日別スケジュール上に空き時間を表示する。
* 予定が入りきらない作業を検出する。
* 「通常勤務内で可能」「残業すれば可能」「前倒しが必要」「そもそも不可能」を判定する。
* 5時終了、6時終了などのパターンを出す。
* 作業候補を前日・翌日・別ラインに移動した場合の再計算をする。
* 人間が最終判断できるように、複数案を提示する。

## J. 生産候補・スケジュール候補の生成

### 実装内容

システムは1つの答えだけでなく、複数の「生成候補」を出し、人が選ぶ形が望まれています。

文字起こしでは、在庫と出荷日を計算し、「この日に作るべき」という数量が出る話がされています。 また、実際に無理な場合はパターンとして出し、人間が確認して判断するという話もあります。

### 要件

* 生産候補を自動生成する。
* 候補には以下を含める。

  * 生産日
  * 商品
  * 数量
  * 作業場所
  * 必要人員
  * 想定作業時間
  * 原料使用予定
  * 在庫推移
  * 出荷充足可否
* 候補ごとに「問題なし」「原料不足」「能力不足」「残業必要」などの状態を表示する。
* 人間が候補を採用・修正・却下できる。
* 採用後、在庫・原料・日報・発注予定に反映する。

## K. 製品在庫管理

### 実装内容

商品在庫をExcelのように見える形で管理し、出荷予定・生産予定・実績によって将来在庫を計算する必要があります。

文字起こしでは、在庫の見え方はExcelと同じような形で、原料在庫・商品在庫を表示し、受注・出荷・月間予定に合わせて数量が出てくる形が説明されています。

### 要件

* 商品別の現在在庫を管理する。
* 受注・出荷予定による在庫減少を自動計算する。
* 生産予定による在庫増加を自動計算する。
* 日報実績による実在庫反映を行う。
* 将来日別の在庫推移を表示する。
* 在庫切れ見込み日を表示する。
* Excelに近い一覧画面を用意する。
* 商品在庫と原料在庫を両方扱う。

## L. 原材料在庫・使用予定・発注管理

### 実装内容

生産予定を組んだ時点で、必要な原材料を計算し、原材料在庫が将来マイナスになる場合は事前にアラートを出す必要があります。

文字起こしでは、今は社員が月間予定を組む際に原料があるか確認して発注しているが、本来は予定を組んだ時点で原料使用予定が反映され、マイナスになるなら発注書が出てきて、それを送るだけにしたい、という話があります。

### 要件

* 商品ごとの原材料構成、BOMを管理する。
* 生産予定から原材料使用予定を自動計算する。
* 原材料の現在在庫を管理する。
* 将来日別の原材料在庫推移を表示する。
* 使用予定反映後にマイナスになる日を検出する。
* 必要発注数量を算出する。
* 発注書を自動作成する。
* 人は発注書を確認して送るだけにする。

## M. 原材料リードタイムを考慮した発注アラート

### 実装内容

原材料がマイナスになった日にアラートを出しても遅いため、材料ごとのリードタイムを登録し、必要発注日を逆算する必要があります。

文字起こしでは、「マイナスになってからでは遅い」「発注してから2週間かかる可能性がある」「1週間前に赤になっても遅い」という話が出ています。

### 要件

* 原材料ごとにリードタイムを登録する。
* 発注単位、最小発注数、安全在庫も登録できるようにする。
* 在庫不足日から逆算して、発注期限日を出す。
* 発注期限を過ぎている場合は緊急アラートにする。
* 「今発注すれば間に合う／間に合わない」を判定する。
* 1か月先、できれば数か月先まで原材料不足を予測する。
* 生産予定変更時に原料不足アラートも再計算する。

## N. 日報の電子化・タブレット入力

### 実装内容

現場の日報を紙からタブレット・iPad入力に変更し、入力された実績をそのまま在庫・生産能力・予測に反映する必要があります。

文字起こしでは、日報入力に時間と人手がかかっているため、現場の日報をパッドにしたい、なるべく人がかからないようにしたい、という話があります。

### 要件

* タブレットで日報入力できる。
* パート・現場担当者が直接入力できる。
* 入力項目は最低限以下。

  * 日付
  * 商品
  * 作業場所
  * 担当者または人数
  * 作業開始時刻
  * 作業終了時刻
  * 休憩
  * 生産数量
  * 不良数
  * 備考
  * トラブル・停止理由
* 入力後、管理者が確認・承認できる。
* 承認後、在庫・実績・生産能力に反映する。
* 紙の日報を取りまとめる作業をなくす。

## O. 実績反映によるスケジュール再計算

### 実装内容

予定数量と実績数量がズレた場合、翌日以降の生産予定を自動で再計算する必要があります。

文字起こしでは、今日3,000できると思ったが2,500しかできなかった、逆に3,500できた、という場合に、実数に切り替わって次に作るべき数量が出る、という話があります。

### 要件

* 日報実績をもとに予定数量との差分を計算する。
* 実績が少なければ、残数量を翌日以降に再配分する。
* 実績が多ければ、翌日以降の予定を減らす。
* 在庫数を実績ベースで更新する。
* 原材料使用量も実績ベースで更新する。
* 生産能力の学習データとして蓄積する。
* 予定と実績の差異をレポート表示する。

## P. 1時間あたり生産量・1人あたり生産量の自動算出

### 実装内容

当初は手動で1時間あたり生産量を入力するが、日報データが溜まってきたら中央値などから自動計算する必要があります。

文字起こしでは、1時間あたりの生産量は今は手動入力だが、日報が溜まれば中央値から自動で取れるようになる、という話があります。 また、前年度データは業務管理から読み込んでおり、足りないのは時間あたりの袋数・1人あたりの情報だという話もあります。

### 要件

* 商品別・作業別・場所別・人数別の生産実績を蓄積する。
* 1時間あたり生産量を自動算出する。
* 1人1時間あたり生産量も算出する。
* 平均値だけでなく中央値を使えるようにする。
* 異常値を除外できる。
* 初期値は手動入力できる。
* 日報実績が増えるほど、能力値を自動更新する。
* 能力値の履歴を残す。
* 自動更新した能力値を人が確認・固定できる。

## R. アラート機能

### 実装内容

| ------ | ----------------------- |

# 4. 特に重要な業務ルール

## 1. 受注生産品と在庫生産品を分ける

受注が来るまで作らない商品と、在庫として先に作る商品はロジックが違うため、商品マスタで明確に区分する必要があります。

## 2. 原材料は「実績」ではなく「予定」の時点で引き当てる

生産が終わってから原材料を減らすだけでは遅く、予定を組んだ時点で使用予定として反映する必要があります。これにより、未来の不足が見えます。

## 3. 発注アラートはリードタイム込みで出す

在庫がマイナスになった日に警告しても間に合わないため、リードタイムを考慮して「いつまでに発注すべきか」を出す必要があります。

## 4. 実績が予定と違ったら次の予定を変える

予定3,000に対して実績2,500なら残りを再計算し、実績3,500なら翌日以降を減らします。これは生産計画だけでなく、在庫・原料・能力値にも反映する必要があります。

## 5. 完全自動ではなく「候補生成＋人の判断」にする

残業するか、17時で終えるか、前倒しするかなどは現場判断が必要なため、システムは複数案を出し、人が採用する設計が現実的です。

# 5. 実装対象外または別枠で扱うべきもの

文字起こし上、以下は話題に出ていますが、生産管理システム本体とは分けた方がよいです。

| 項目              | 扱い                    |
| --------------- | --------------------- |
| ChatGPT有料版・AI研修 | システム本体とは別相談           |
| Windows 7 PCの更新 | インフラ・端末更新として別管理       |
| Wi-Fi改善         | タブレット日報導入の前提条件として要確認  |
| TikTok紹介・費用の話   | 生産管理要件とは別             |
| 請求・支払いスケジュール    | 契約・経理管理であり、システム機能ではない |

ただし、タブレット日報を導入するなら、Wi-Fiが倉庫・現場まで届くかは事前確認が必要です。

# 9. まとめ

実装すべきシステムは、単なる在庫管理ではなく、**在庫管理・生産計画・日報・原材料発注・需要予測を一体化した生産管理システム**です。

最重要ポイントは以下です。

* 月間生産予定を自動算出する。
* 月間数量を日別・現場別に自動割り振りする。
* 受注・出荷・在庫・日報・シフトを連動させる。
* 原材料不足をリードタイム込みで事前警告する。
* 日報をタブレット化し、実績を翌日以降の予定に反映する。
* 生産能力は日報実績から徐々に自動算出する。
* 完全自動ではなく、候補を出して人が確認・承認する設計にする。
* 手動で残る部分と、将来自動化される部分を明確に見せる。

この内容で進めるなら、まずは **「商品・原料・BOM・在庫・生産能力・シフト・日報・業務管理連携」のデータ設計** を固めることが最優先です。データ構造が固まらないと、月間予測、日別割り振り、原料発注、実績再計算のすべてが不安定になります。
